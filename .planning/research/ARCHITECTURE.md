# Architecture Research

**Domain:** Luxury real-estate marketing site + sales operations platform
**Researched:** 2026-10-23
**Confidence:** HIGH for stack, Next.js 16, Payload, and Vercel constraints; MEDIUM for domain modeling and Philippine regulatory specifics

## Executive Recommendation

Build **one Next.js 16 application** containing three route-group surfaces:

1. **Public site** — statically generated/ISR, locale-aware, cinematic, no authenticated or price data in the payload.
2. **`/ops` console** — dynamic, authenticated, server-rendered operations UI backed by domain services and Payload's Local API.
3. **Payload `/admin`** — content editing and collection administration, generated by Payload inside its own route group.

Use **one Postgres database**, **one user collection**, **one permission model**, and **one durable job system**. The single-app approach is the right default because the public site, content admin, and operations console share the same schema, migrations, auth cookie, and deployment. The conditions that make it safe are strict route-group boundaries, a mandatory data-access layer, no direct database access from UI code, and no Payload admin UI imports into `/ops`.

Do **not** split into microservices, a separate admin app, or a separate API service at launch. Revisit only if the residents portal needs a hard compliance boundary, the internal user base exceeds roughly 10,000, or release cadence genuinely diverges.

### Runtime and Deployment Constraints

These constraints shape the architecture more than any diagram:

- **No long-lived Node server.** Vercel Functions are ephemeral. Payload `jobs.autoRun` must not be used in production. A cron-triggered route or command must run queued jobs.
- **Function duration is finite.** Vercel Functions can run up to 30 minutes, but most routes should finish in seconds. Set `maxDuration` deliberately on the job runner; never put a long export or KYC poll in a request path.
- **Cron is imprecise and has no retries.** Hobby allows once per day with ±59-minute precision; Pro/Enterprise allow once per minute. SLA timers must be computed from timestamps when read, not fired by cron.
- **Database connections are the first serverless failure mode.** Use a `pg` Pool with `attachDatabasePool` from `@vercel/functions` in `instrumentation.ts`. Use the pooled `DATABASE_URL` for the app and the unpooled `DATABASE_URL_UNPOOLED` for migrations.
- **Build-time migrations are required.** Run `payload migrate` before `next build` in CI. Use `push: false` in production. Do not run `prodMigrations` at cold start.
- **Region pairing matters.** Deploy Vercel functions in `sin1` (Singapore) and Neon in `ap-southeast-1` to keep Philippines traffic and database round trips reasonable.
- **The proxy is not a security boundary.** Next.js documentation is explicit that authorization must be verified close to the data and in each Server Function. Proxy runs before routes, may run on CDN infrastructure, and cannot be trusted as the only gate.

### Structure Rationale

- **Three route groups, three root layouts:** `(site)`, `(ops)`, and `(payload)` have different rendering, caching, security-header, and UI needs. A single `app/layout.tsx` would force shared assumptions and leak admin/site styling. Do not create a root `app/layout.tsx` when using this structure.
- **`(payload)` is generated and owned by Payload:** Keep it isolated. Do not import from `@payloadcms/ui` into `/ops`; admin UI packages are not a component library and can pull in server-only assumptions.
- **`modules/` owns business rules:** UI, route handlers, jobs, and Payload hooks call services rather than duplicating queries and invariants. This is where transaction boundaries, state transitions, and audit/consent writes live.
- **`collections/` owns schema and field-level access:** Collection definitions stay declarative. Cross-collection business logic belongs in `modules/`, not in `afterChange` hooks.
- **`access/` is shared by both surfaces:** The same role and permission functions must guard Payload access and `/ops` DAL calls. This avoids two divergent authorization models.
- **`jobs/` is separate from request code:** Jobs are the only place for external side effects and cache revalidation after commit. This keeps request latency and transaction correctness predictable.
- **No direct database access from UI:** `/ops` pages and Server Actions call services. Only services and migrations touch SQL; Payload's Local API is the default data interface.

## Architectural Patterns

### Pattern 1: Route-Group Isolation with Separate Root Layouts

**What:** Each product surface gets its own route group and root layout. Public pages are statically rendered or ISR; `/ops` and `/admin` are dynamic and `no-store`.
**When to use:** Always in this project. The public marketing site and internal console have incompatible caching, CSP, navigation, and error-handling requirements.
**Trade-offs:** Some duplication in layout primitives, but much lower risk of leaking admin code or auth data into public bundles.

**Example:**

```text
app/(site)/[locale]/layout.tsx   → public shell, fonts, analytics, static metadata
app/(ops)/layout.tsx             → auth gate, ops shell, no-store
app/(payload)/layout.tsx         → Payload admin shell
```

### Pattern 2: Data Access Layer as the Authorization Boundary

**What:** Every `/ops` page, Server Action, and route handler calls a single `requireUser(permission)` helper. That helper resolves the Payload session, checks role and permission, and returns a scoped context. Services then use the Local API with `overrideAccess: false` and the current user, or an explicit authorized override.
**When to use:** Every authenticated read and write. Proxy checks are only a redirect optimization.
**Trade-offs:** One extra function call per operation, but it prevents the most dangerous Payload failure mode: Local API access bypass.

**Example:**

```ts
// src/lib/auth.ts — conceptual
import { headers } from "next/headers";
import { getPayload } from "payload";
import config from "@/payload.config";
import { can, type Permission } from "@/access";

export async function requireUser(permission: Permission) {
  const payload = await getPayload({ config });
  const { user } = await payload.auth({ headers: await headers() });

  if (!user || !can(user, permission)) {
    throw new Error("FORBIDDEN");
  }

  return { payload, user };
}
```

```ts
// src/modules/leads/service.ts — scoped Local API read
const { payload, user } = await requireUser("leads:read");
const result = await payload.find({
  collection: "leads",
  user,
  overrideAccess: false,
  where: { assignedTo: { equals: user.id } },
});
```

### Pattern 3: Transactional Outbox + Durable Jobs

**What:** A business transaction writes its state change and a job record in the same Postgres transaction. The job worker performs email, webhook, KYC sync, or cache revalidation after commit. Failures retry without lying about the business state.
**When to use:** Every side effect that must not be lost or must not fire before commit: sales notification, tour confirmation, revalidation, webhook processing, KYC status sync.
**Trade-offs:** More moving parts and eventual consistency for notifications. Much safer than sending email inside `afterChange`, where a rollback can occur after the email is sent.

**Why this is mandatory in Payload:** `afterChange` hooks run inside the transaction. An unawaited async hook can complete after a rollback and report success for a write that no longer exists. Inline `revalidatePath` can also publish stale content because the transaction has not committed yet.

**Example:**

```ts
// Conceptual hook: enqueue inside the same transaction.
// Verify the exact jobs.queue signature against the installed Payload version.
const afterLeadCreated: CollectionAfterChangeHook = async ({
  doc,
  operation,
  req,
}) => {
  if (operation !== "create") return doc;

  await req.payload.jobs.queue({
    task: "notify-sales",
    input: { leadId: doc.id },
    req, // participate in the same transaction where supported
  });

  return doc;
};
```

The worker, not the hook, calls `revalidateTag`/`revalidatePath`, sends email, or calls a provider.

### Pattern 4: Split CSP and Rendering Strategy

**What:** The public site uses a static CSP without a per-request nonce, allowing static generation and ISR. `/ops` and `/admin` use a strict nonce-based CSP and dynamic rendering.
**When to use:** When the marketing site must be cacheable but internal surfaces handle PII and need stronger script control.
**Trade-offs:** The public CSP is weaker on inline script control unless hashes are added later. A single nonce CSP for the whole app would force every public page dynamic and destroy the performance strategy.

**Example:**

```text
Public:  script-src 'self' 'unsafe-inline'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
Ops/Admin: script-src 'nonce-<random>' 'strict-dynamic'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'
```

Treat the public `'unsafe-inline'` as an explicit v1 trade-off, not a permanent ideal. Add hash-based CSP for the known inline scripts once the public bundle stabilizes.

### Pattern 5: Append-Only Ledgers for Trust Data

**What:** Audit events, consent events, price events, and inventory events are append-only. Current state is derived from the latest event or maintained in a materialized state row within the same transaction.
**When to use:** Audit logs, consent history, price history, inventory status changes, reservation state changes.
**Trade-offs:** More rows and more careful query design. It is the only defensible way to answer "who changed this, when, under which policy, and with what consent?"

**Example:**

```text
consent-events: subject, purpose, action, policyVersion, evidence, capturedAt
consent-state:  subject, purpose, currentAction, latestEventId, updatedAt
```

Never update or delete `consent-events` or `audit-events` through application code. Revoke `UPDATE`/`DELETE` at the database role level for defense in depth.

### Pattern 6: Locale Rewrite, Not Redirect Chains

**What:** English is the default locale and is served unprefixed. The proxy rewrites `/about` to `/en/about` internally. Filipino is explicit at `/fil/about`.
**When to use:** Launch localization for English and Filipino while preserving legacy URL equity.
**Trade-offs:** Rewrites are invisible to users and avoid redirect chains, but every internal link must use the canonical localized helper. A misconfigured matcher can rewrite assets or API routes.

**Example:**

```ts
// proxy.ts — conceptual
export function proxy(request: NextRequest) {
  const { pathname } = request.nextUrl;

  if (
    pathname.startsWith("/ops") ||
    pathname.startsWith("/admin") ||
    pathname.startsWith("/api") ||
    pathname.startsWith("/_next") ||
    pathname.includes(".")
  ) {
    return NextResponse.next();
  }

  if (pathname === "/fil" || pathname.startsWith("/fil/")) {
    return NextResponse.next();
  }

  const url = request.nextUrl.clone();
  url.pathname = `/en${pathname === "/" ? "" : pathname}`;
  return NextResponse.rewrite(url);
}
```

Keep the matcher narrow and exclude `/api`, especially upload and webhook routes, to avoid proxy body buffering.

### Request Flow: Server Action / Mutation

```text
Form submits Server Action
    ↓
requireUser(permission)
    ↓

    ↓
domain service opens a transaction
    ├── lock/read the aggregate
    ├── enforce state transition and invariants
    ├── write business row
    ├── append audit event
    ├── append consent event (if applicable)
    └── enqueue outbox job (same transaction)
    ↓
commit
    ↓
return typed result to useActionState
    ↓
job worker later sends email / revalidates / calls provider
```

### Request Flow: Webhook

```text
Provider POST /api/webhooks/[provider]
    ↓
verify signature against raw body
    ↓
insert or ignore webhook-events row by provider event ID (idempotency)
    ↓
enqueue process-webhook job
    ↓
202 Accepted
    ↓
worker loads event, calls domain service, records result
```

Webhook routes must not run through the proxy body buffer. Keep `/api` out of the proxy matcher.

### Request Flow: Cron / Job Runner

```text
Vercel Cron (once per minute on Pro)
    ↓
GET /api/cron/jobs with Authorization: Bearer CRON_SECRET
    ↓
payload.jobs.run({ queue, limit })
    ↓
job handler
    ├── notify-sales
    ├── send-tour-confirmation
    ├── revalidate-content
    ├── process-webhook
    ├── sync-kyc
    └── retention-purge
    ↓
mark job complete / retry with backoff
```

Cron is a wake-up mechanism, not a scheduler for business deadlines. Tour reminders, SLA breaches, and hold expiry are computed from stored timestamps.

### State Management

- **Server state is the source of truth.** Postgres/Payload owns content, leads, inventory, consent, and audit. The client never becomes authoritative.
- **URL is the primary UI state.** Filters, pagination, selected pipeline stage, and date ranges belong in search params so `/ops` views are linkable and refresh-safe.
- **Server Components by default.** Client components are limited to interactive islands: calendar pickers, filters, charts, 360 viewers, and optimistic form controls.
- **Server Actions for mutations.** Use `useActionState` for pending/error states. Do not build a parallel REST API for the ops UI.
- **No global client store at launch.** React Context is enough for the ops shell (current user, permissions, toasts). Add a client cache only if a measured interaction requires it.
- **Draft preview uses `draftMode()`.** Preview bypasses public caches and must never be available to anonymous users.
- **No sensitive data in client state.** Price, KYC status, and client PII are fetched server-side per request and never placed in localStorage.

### Key Data Flows

1. **Lead capture and attribution:** Public form → Server Action → consent validation → normalization/dedupe → `leads` + `lead-activities` + `consent-events`/`consent-state` → outbox job → sales email + `/ops` inbox. First-touch and last-touch UTM values are stored separately; the landing page and referrer are captured server-side.
2. **Tour booking:** Lead selects a unit type and slot → availability service checks capacity and existing bookings → `tours` row + hold/confirmation → outbox job sends confirmation and creates an ops task. Calendar sync is deferred; the internal calendar is authoritative.
3. **Reservation and KYC:** Sales creates a draft reservation → unit hold is validated under a database constraint → KYC check is requested → provider webhook/job updates `kyc-checks` → approval requires KYC `approved` or `not-required` → reservation becomes `reserved`; documents remain private.
4. **Content publishing:** Editor publishes in `/admin` → Payload `afterChange` enqueues `revalidate-content` → worker resolves tags and calls `revalidateTag`/`revalidatePath` after commit → CDN serves fresh HTML.
5. **Consent and audit:** Every PII write and every consent change appends an event. Current consent is a materialized projection; audit is immutable. Both writes join the business transaction so a failed audit/consent write rolls back the operation.
6. **Price and inventory history:** Price changes append `price-events`; status changes append `inventory-events`. Current values are query projections or maintained fields, never the only record.

| Content | `media`, `documents`, `pages`, `unit-types`, `towers`, `amenities`, `news-posts`, `site-settings`, `navigation`, `legal-documents` | Public content, SEO, localized copy, media metadata | Published content is public-read only; drafts require auth |
| Inventory | `units`, `unit-prices`, `price-events`, `holds`, `reservations` | Physical units, commercial state, price history, reservation lifecycle | A unit cannot have two active holds or confirmed reservations |
| CRM | `leads`, `clients`, `lead-activities`, `tours`, `tasks`, `pipeline-stages`, `scoring-rules`, `enrichment-runs` | Demand, attribution, interactions, ownership, scoring | A lead has one current owner and one canonical client link |
| Trust | `audit-events`, `consent-events`, `consent-state`, `kyc-checks`, `data-subject-requests`, `retention-policies` | Immutable history, lawful basis, KYC status, DSAR/retention workflow | Audit and consent events are append-only |
| Operations | `webhook-events`, `outbox-events` (or Payload jobs collection) | Idempotency and reliable side effects | One provider event ID is processed once; jobs survive deploys |
| Residents (later) | `residents`, `resident-units`, `service-requests`, `announcements`, `facility-bookings`, `resident-documents` | Post-turnover resident services | Separate auth collection and cookie; no access to sales PII |

### Content Collections

- **`pages`** — block-based editorial pages, localized fields, SEO group (`title`, `description`, `ogImage`, `canonical`, `noindex`), draft/published status, `legacyUrl`.
- **`unit-types`** — exactly 12 records; name, slug, tower(s), area breakdown (interior, balcony, total), floor plan media, gallery, 360 tour reference, description, SEO, display order. Pricing is not a public field.
- **`towers`** — North/South/etc., floor count, unit count, amenities, gallery, location copy.
- **`amenities`** — name, category, description, image, display order, available-at-handover flag.
- **`news-posts`** — title, slug, excerpt, body, hero, author (staff display name only), publishedAt, SEO, `legacyUrl`. Exactly 58 legacy records must map.
- **`site-settings`** / **`navigation`** — global editorial configuration. Keep these small; do not turn them into a page builder.
- **`legal-documents`** — versioned privacy policy, terms, consent copy, cookie policy. Each version has a content hash used by consent evidence.
- **`documents`** — metadata for brochures, floor plans, and legal PDFs; `visibility` is `public` or `private`; private documents require a signed URL route.
- **`media`** — public Blob-backed images and files, dimensions, alt text, focal point, blur placeholder, MIME validation.

### Inventory and Commercial Collections

- **`units`** — unit number, tower, floor, unit type, interior/balcony area, orientation, view, status (`not-released`, `available`, `held`, `reserved`, `sold`), handover estimate, notes. Unique `(tower, unitNumber)`.
- **`unit-prices`** — current price per unit, integer PHP centavos, currency, effective date, visibility. Read access is restricted to sales/compliance/admin. This is a separate collection, not a public field on `units`.
- **`price-events`** — append-only: unit, old price, new price, currency, reason, actor, timestamp. Never mutate.
- **`holds`** — unit, lead/client, owner, `expiresAt`, status (`active`, `released`, `converted`, `expired`), reason. Active holds are protected by a Postgres exclusion constraint on `(unit_id, tstzrange)`.
- **`reservations`** — unit, client, status (`draft`, `pending-approval`, `approved`, `reserved`, `cancelled`, `expired`), reservation fee reference, KYC check, document checklist, sales owner, timestamps. A partial unique index prevents more than one active reservation per unit.
- **`inventory-events`** — append-only status transitions with actor, reason, and timestamp.

### CRM Collections

- **`leads`** — contact fields (name, email, normalized email, phone, normalized phone), source, first-touch and last-touch UTM, landing page, referrer, consent summary, score, status, owner, SLA timestamps, client link, `mergedInto`. Do not store the entire interaction history here.
- **`clients`** — canonical person/account, primary contact, nationality, locale, KYC status, consent summary, merged lead IDs, household/company links. One client can have many leads.
- **`lead-activities`** — append-only timeline: call, email, WhatsApp/Viber note, tour, stage change, assignment, note, consent change. Actor, channel, summary, metadata, timestamp.
- **`tours`** — lead/client, unit types of interest, date/time, duration, gallery/location, assigned agent, capacity, status (`requested`, `confirmed`, `completed`, `no-show`, `cancelled`), confirmation timestamps.
- **`tasks`** — follow-up, document request, KYC review, reservation approval; owner, due date, priority, status, related record.
- **`pipeline-stages`** — ordered configuration: new, contacted, qualified, tour-booked, toured, reservation, reserved, sold, nurture, lost. Stage changes are recorded in `lead-activities`.
- **`scoring-rules`** — explicit, versioned rules over declared data and behavior (budget band, timeline, unit type, source, engagement). No covert scoring.
- **`enrichment-runs`** — consent basis, provider, fields enriched, result, timestamp. Enrichment must be traceable to a consent purpose.

### Trust and Compliance Collections

- **`audit-events`** — actor, action, collection, `docId`, before/after redacted diff, request ID, IP hash, user agent hash, timestamp, outcome. Append-only; read restricted to compliance/admin.
- **`consent-events`** — subject, purpose (`marketing`, `analytics`, `enrichment`, `kyc`, `data-sharing`), lawful basis, policy version/hash, action (`granted`, `withdrawn`, `expired`), channel, evidence snapshot, IP hash, user agent, URL, capturedAt, expiresAt. Append-only.
- **`consent-state`** — projection: subject, purpose, current action, latest event, updatedAt. Updated in the same transaction as the event.
- **`kyc-checks`** — subject/client, provider, level, status (`not-started`, `pending`, `approved`, `rejected`, `expired`, `manual-review`), provider reference, checks summary, PEP/sanctions flags, expiry, reviewer. Do not store raw ID numbers.
- **`data-subject-requests`** — request type (access, correction, erasure, objection, portability), status, due date, evidence, resolution, redaction notes.
- **`retention-policies`** — data class, retention period, legal basis, purge action, last run. Retention jobs are audited.
- **`webhook-events`** — provider, external event ID (unique), payload hash, status, attempts, processedAt, error. This is the idempotency ledger.

### Critical Schema Decisions

1. **Money is integer centavos.** Store `priceCentavos` as `bigint`/integer plus `currency: "PHP"`. Never use floats for prices or fees.
2. **Public identifiers are stable slugs; internal joins use IDs.** Keep `legacyUrl` on unit types and news posts for redirect generation and analytics continuity.
3. **Use Postgres extensions deliberately:** `pgcrypto` for UUIDs/hashes, `citext` for case-insensitive email, `pg_trgm` for admin search, `btree_gist` for hold exclusion constraints.
4. **Normalize contact data at write time.** Lowercase/trim email, E.164 phone, and store both raw and normalized values. Use unique partial indexes for active records.
5. **Dedupe is a workflow, not a blind upsert.** Match on normalized email/phone/name; auto-link only high-confidence matches; queue ambiguous matches for human review; record every merge in audit and preserve `mergedInto`.
6. **Inventory concurrency is enforced in the database.** Application checks alone will race. Use an exclusion constraint for active holds and a partial unique index for confirmed reservations, then wrap the service in a transaction with row locks.
7. **Append-only means append-only.** Revoke `UPDATE`/`DELETE` on audit/consent/price-event tables from the application role. Corrections are new events with a reason.
8. **Avoid giant documents.** Payload JSONB is convenient, but lead history, consent, and audit must be relational rows for querying and retention. Keep JSON for flexible metadata, not for the core ledger.
9. **PII minimization is a schema concern.** Do not add fields "just in case." Date of birth, government ID, and financial data require a documented purpose, access rule, and retention period.
10. **Soft-delete only where recoverability matters.** Prefer explicit status/archived fields for content. Never soft-delete audit/consent events.

### Lead, Reservation, and KYC State Machines

```text
Lead:
new → contacted → qualified → tour-booked → toured → reservation-pending
   ↘ nurture ↗
   ↘ lost (reason required)

Reservation:
draft → pending-approval → approved → reserved
   ↘ cancelled / expired (reason required)

KYC:
not-started → pending → approved
                    ↘ manual-review → approved / rejected
                    ↘ expired → pending

Rules:
- A reservation cannot move to approved until KYC is approved or not-required.
- A unit cannot have two active holds or two active reservations.
- Every state change appends an activity/audit event with actor and reason.
- Expiry is computed from timestamps; a cron job may clean up, but reads must treat expired holds as inactive.
```

## Authentication, Authorization, and Audit

### Role Model

| Role | Intended user | Allowed surface | Explicit limits |
|------|---------------|-----------------|-----------------|
| `admin` | Platform owner / lead developer | Everything, user management, settings, migrations | Break-glass only; actions audited |
| `content-editor` | Client marketing | Pages, unit types, amenities, news, media, SEO | No leads, pricing, reservations, or audit |
| `marketing` | Campaign manager | Campaigns, source/UTM reporting, lead aggregates | PII masked unless granted; no price edits |
| `sales-manager` | Sales head | All leads, tours, pipeline, inventory, reservations, reports | No user administration or audit deletion |
| `sales-agent` | Front-line sales | Assigned leads, tours, own reservations | No unassigned client PII, no price changes, no KYC approval |
| `compliance` | DPO / compliance officer | Audit, consent, KYC status, DSARs, retention | No commercial edits; read-only client data except KYC workflow |
| `resident-manager` | Post-turnover staff | Residents, service requests, announcements, bookings | No sales CRM or pricing access |

Keep permissions granular (`leads:read`, `leads:assign`, `pricing:read`, `pricing:write`, `reservations:approve`, `kyc:review`, `audit:read`, `consent:write`, `settings:manage`) and map roles to permissions in one module. Do not scatter role-name string checks across the codebase.

### Authorization Layers

1. **Proxy:** cheap redirect if `/ops` has no session cookie; security headers; locale rewrite. No role logic.
2. **Route layout:** `requireUser("ops:access")` for the ops shell. This prevents rendering navigation to unauthorized users.
3. **Page/action:** `requireUser("<specific permission>")` on every page, Server Action, and route handler.
4. **Service:** row-level scoping and field redaction based on the actor. A sales agent query includes `assignedTo = user.id`; a manager query does not.
5. **Payload collection access:** defense in depth. Collection access functions must reject writes from roles that should not use REST, even if a route is misconfigured.
6. **Database:** least-privilege role for the app; separate migration role; revoke destructive privileges on append-only tables.

The critical failure to avoid is treating Payload's Local API as automatically authorized. It is not. `overrideAccess` defaults to `true` for Local API calls. Every `/ops` call must pass the user and `overrideAccess: false`, or go through a service that has already made an explicit, documented authorization decision.

### Sessions and Login

- Staff authenticate against the Payload `users` collection. The `payload-token` cookie is httpOnly, secure, and `SameSite=Lax`; set `Path=/` so it is available to both `/ops` and `/admin`.
- Enable `useSessions: true` so sessions are revocable. A password change or role change should revoke active sessions.
- `/ops/login` calls Payload login (Local API or REST) and sets the cookie server-side. Do not expose a separate credential store.
- Logout clears the cookie and records an audit event.
- Login throttling uses Payload's `maxLoginAttempts` plus a Postgres-backed rate limit keyed by IP hash and email hash. Do not rely on in-memory counters in serverless.
- Residents use a **separate auth collection and separate cookie** (for example `velaris-resident-token`) with `access.admin: false`. This prevents a resident session from being interpreted as a staff session and keeps the future portal isolated.

### Audit Log Design

- Write audit events from hooks *and* from services for actions that do not map to a single collection write (login, export, document view, KYC review, DSAR decision).
- Pass the active `req` into the audit write so it joins the same transaction. If the audit write fails, the business operation must fail.
- Redact secrets and sensitive fields before storing diffs. Never store raw ID numbers, full request bodies, or passwords.
- Record actor ID, actor role, action, target collection, target ID, outcome, request ID, IP hash, and user agent hash.
- Read access is limited to `admin` and `compliance`. There is no update or delete API.
- Optional hash chaining adds tamper evidence but introduces serialization and concurrency complexity. Skip it at launch; database privilege separation is the higher-value control.

### Consent Ledger Design

- Consent is purpose-specific. A marketing opt-in does not authorize enrichment, analytics, or KYC.
- Each event captures the exact policy version and a hash of the consent copy shown. A later policy change does not retroactively rewrite consent.
- Withdrawal appends a new event and updates `consent-state`; it does not delete the grant history.
- Downstream jobs check current consent before enrichment, marketing email, or analytics export.
- Consent evidence should be sufficient to reconstruct what the user saw: form ID, policy version, timestamp, channel, URL, and a redacted snapshot.

## Background Jobs and Serverless Constraints

### Job Inventory

| Job | Trigger | Idempotency key | Timeout / notes |
|-----|---------|-----------------|-----------------|
| `notify-sales` | Lead created | `lead:{id}:notify` | Fast email/queue call; retry on provider failure |
| `send-lead-acknowledgement` | Lead created | `lead:{id}:ack` | Only if consent/marketing purpose allows |
| `send-tour-confirmation` | Tour confirmed | `tour:{id}:confirm` | Include calendar attachment or link |
| `send-tour-reminder` | Scheduled scan | `tour:{id}:reminder:{date}` | Compute due reminders from timestamps |
| `revalidate-content` | Publish/unpublish | `content:{collection}:{id}:{updatedAt}` | Runs after commit; tags resolved in worker |
| `process-webhook` | Provider webhook | `provider:{eventId}` | Must be safe to retry; store raw payload hash |
| `sync-kyc` | KYC request or webhook | `kyc:{checkId}:{status}` | Polling fallback for missed webhooks |
| `enrich-client` | Consent + manual action | `enrichment:{clientId}:{ruleVersion}` | Record provider, fields, consent basis |
| `retention-purge` | Daily cron | `retention:{policyId}:{date}` | Dry-run mode; audit every deletion |
| `sla-scan` | Optional cron | `sla:{date}:{bucket}` | Notifications only; breach state is computed on read |

### Serverless Rules

- **No `autoRun`.** Payload's in-process job runner assumes a long-lived server. On Vercel, trigger `payload.jobs.run()` from `/api/cron/jobs` or a scheduled command.
- **One cron entry at launch.** A single once-per-minute cron can drain multiple queues with limits. This stays under Vercel's 100-cron limit and avoids duplicated schedules.
- **Cron on Hobby is not production-grade for this app.** Hobby's once-per-day cadence and ±59-minute precision are incompatible with timely lead notifications. Use Pro or trigger jobs from the request path for time-sensitive work, with a durable fallback.
- **Cron does not retry.** Retries must live in Payload jobs. If the cron request fails, the next minute's run drains the backlog.
- **Set `maxDuration` intentionally.** The job route may need 60–300 seconds; lead capture routes should be short. Never run a 30-minute export inside a user request.
- **Do not hold a database transaction across an external call.** Commit first, then call the provider in a job. If the provider must be called during the request, use an idempotency key and accept eventual consistency.
- **Use the pooled connection string in functions.** `attachDatabasePool` releases idle clients before suspension. The unpooled URL is only for migrations and administrative scripts.
- **Warm-up is not a strategy.** Assume cold starts. Keep the Payload singleton initialization cheap and avoid top-level heavy imports in route modules.

### Why Not Vercel Queues or Workflows at Launch

Vercel Queues (Beta) and Vercel Workflows (GA) are credible options for durable execution, but adding them now creates a second job system alongside Payload's Postgres-backed queue. For a small team, one observable queue is better. Revisit when:

- job volume exceeds what a once-per-minute drain can handle,
- jobs need multi-step waits longer than a function lifetime,
- or the team needs independent scaling of the worker.

If that happens, keep Payload jobs as the transactional outbox and hand off long-running orchestration to Workflows.

## Caching, Rendering, and Localization

### Rendering Matrix

| Surface | Rendering | Cache | Revalidation | Auth |

| Home, About, Amenities, Location, Developer | Static / ISR | CDN + Full Route Cache | On publish + time-based fallback | None |

| News posts (58) | `generateStaticParams` + ISR | CDN | On publish | None |

| Brochure gate | Static shell + Server Action | No PII cache | N/A | Lead cookie/token |
| `/ops/*` | Dynamic | `no-store` | N/A | Required |
| `/admin/*` | Dynamic | `no-store` | N/A | Payload |
| `/api/*` | Dynamic | `no-store` | N/A | Varies |
| Private documents | Dynamic route | `no-store` | N/A | Signed URL + permission |

### Caching Decision

**Disable `cacheComponents` and `partialPrefetching` for v1.** Payload's admin is not fully compatible with Cache Components, and the known issues (status codes, Activity DOM, test tooling) are not worth the risk during initial delivery. Use the mature path:

- Static generation for known pages.
- `revalidate = false` for evergreen pages plus on-demand invalidation.
- `revalidate = 3600` for news indexes.
- `unstable_cache` with tags for shared public queries.
- `revalidateTag`/`revalidatePath` from a job after commit.

Revisit Cache Components after Payload publishes full compatibility guidance and the admin route group can be verified in staging.

### Public Pages Must Stay Cookie-Free

Reading `cookies()`, `headers()`, or `searchParams` in a public page opts it into dynamic rendering. Keep locale in the path via proxy rewrite, not in a cookie. If personalization is needed later, isolate it in a small client component or a separate dynamic route; do not make the whole page dynamic.

### Localization

- Payload localization: `en` (default) and `fil`, with fallback to `en`.
- Localized fields: page copy, unit-type descriptions, amenities, news body, SEO title/description, navigation labels, form labels.
- Routing: `/[locale]` for both languages internally; the proxy rewrites unprefixed English paths to `/en/...`. `/fil/...` is explicit.
- Canonical URLs: English unprefixed, Filipino prefixed. Add `hreflang` alternates and self-canonical on every page.
- `generateStaticParams` returns both locales for static pages.
- Do not redirect based on `Accept-Language`; it breaks crawlability and shared links. Offer a visible language switch.
- Keep `/ops` and `/admin` English-only at launch; internal UI localization is not a requirement.

### Legacy URL Preservation

- Generate a static redirect map in `next.config.ts` `redirects()` for the 12 legacy unit pages and 58 news posts. Use permanent redirects to the new canonical URLs: `permanent: true` (308) by default, or an explicit `statusCode: 301` if the SEO tooling requires 301. Do not use temporary redirects.
- `redirects()` runs before the proxy, which makes it the cheapest and most reliable layer for a fixed legacy set.
- Store `legacyUrl` on the destination record so the map can be generated and audited. Do not hand-maintain two disconnected lists.
- Avoid locale redirect chains: `/old-unit` should go directly to `/residences/new-slug`, not `/old-unit` → `/en/old-unit` → `/residences/new-slug`.
- If editorial redirects are added later, store them in a small collection and resolve them in the proxy with a cached map. Do not add a database query to every request.

## Media, Documents, and Private Data

### Public Media

- Use the Payload Vercel Blob adapter for public media: `disableLocalStorage: true`, image sizes, sharp, and `remotePatterns` for the Blob host.
- Generate AVIF/WebP variants; set `minimumCacheTTL` to roughly 30 days; use `priority` only for the LCP hero.
- Store alt text, focal point, and blur placeholder in Payload. Enforce MIME allowlists and strip EXIF on upload.
- Reuse the existing Pano2VR tour assets under `public/tours/` or immutable Blob storage. Load the viewer only on interaction to protect LCP.
- Video needs a dedicated provider (Mux) or pre-optimized MP4. Vercel Blob does not transcode; do not upload raw camera files.

### Private Documents and KYC

**Do not use `@payloadcms/storage-vercel-blob` for private documents.** The adapter does not support Vercel Private Blob access (feature request `#16319`). Use one of these patterns:

1. **Preferred:** Do not custody KYC documents. The KYC provider stores them; your database stores only the check reference, status, and redacted results.
2. **If documents must be stored:** Use `@vercel/blob` directly with `access: "private"`, a server-only route that checks permission, issues a short-lived signed URL, and writes an audit event for every view.
3. **Brochures:** Private Blob + lead-gated signed URL. Do not use public Google Drive links.
4. **Reservation documents:** Private Blob, permission-scoped, with a retention policy and audit trail.

Private document routes must be `no-store`, must not be guessable, and must never appear in public sitemaps or RSC payloads. Treat every document view as a reportable access event.

## Scaling Considerations

This is not a consumer-scale product. A realistic launch is hundreds to a few thousand leads per month, a few dozen internal users, and a content archive in the low hundreds of records. The architecture should stay boring far longer than a typical SaaS design.

| Scale | Architecture adjustment |
|-------|-------------------------|
| 0–1k leads/month, <25 staff | Single Next app, single Neon instance, single job queue, ISR, Blob. No read replica, no separate worker, no microservices. |
| 1k–100k leads/month, 25–100 staff | Tune image variants and cache hit rate; add indexes for pipeline/KPI queries; increase job drain limits; consider a dedicated worker invocation or Vercel Queues; add materialized views for KPIs; consider Neon read replica for reporting. |
| 100k+ leads/month or multi-project | Split the job runner into its own deployment; move analytics/BI to a read replica or warehouse; consider a separate residents portal if compliance/release cadence demands it; add search infrastructure if admin search degrades. Do not split the public site from its content API without measured need. |

### Scaling Priorities

1. **First bottleneck: image optimization and media weight.** Luxury photography is the product. Enforce responsive sizes, AVIF/WebP, lazy loading below the fold, `priority` only on the hero, and immutable Blob caching. A beautiful page that ships 5 MB of images fails the LCP target.
2. **Second bottleneck: database connections and cold starts.** Serverless concurrency multiplies connections. `attachDatabasePool`, pooled URLs, and short transactions matter before any query optimization.
3. **Third bottleneck: background job latency.** A once-per-minute cron is fine at launch. If lead notifications or webhook processing back up, increase drain limits, separate queues, or move long-running orchestration to Workflows.
4. **Fourth bottleneck: KPI queries.** Dashboards that aggregate the entire lead/activity table on every request will degrade. Start with indexed counts and date-bounded queries; add materialized views when measured.
5. **Fifth bottleneck: admin search and dedupe.** `pg_trgm` indexes and normalized columns handle the first tens of thousands of records. Add a search service only after measuring.

### What Not to Optimize Prematurely

- Do not add Redis unless rate limiting or session caching is measured as a bottleneck. Postgres can handle the launch load.
- Do not add a separate API service for the ops UI. Server Actions and services are sufficient.
- Do not add event streaming or Kafka. The transactional outbox is the event log until volume proves otherwise.
- Do not shard by tower or locale. The data is small and relational.

## Anti-Patterns

### Anti-Pattern 1: Proxy-Only Authorization

**What people do:** Check the `payload-token` cookie in `proxy.ts` and assume `/ops` is protected.
**Why it's wrong:** The proxy can be bypassed by matcher changes, runs before route logic, and is not a reliable authorization boundary. Next.js documentation explicitly requires verification in each Server Function/DAL.
**Do this instead:** Use the proxy only for a coarse redirect and security headers. Call `requireUser(permission)` in every ops layout, page, Server Action, and route handler, then enforce row-level scope in the service.

### Anti-Pattern 2: Trusting Payload's Local API Access Defaults

**What people do:** Call `payload.find()` or `payload.update()` from a server component without passing a user, assuming collection access rules apply.
**Why it's wrong:** Local API bypasses access control by default (`overrideAccess: true`). A sales agent could read every lead or change a price if the route forgets a check.
**Do this instead:** Centralize access in a service. Pass `user` and `overrideAccess: false` for every user-scoped operation. Use `overrideAccess: true` only in a documented internal job or public-content read with a narrow projection.

### Anti-Pattern 3: Putting Prices in the Public Page Payload

**What people do:** Fetch the full unit document, including price, and hide it with CSS or a client-side auth check.
**Why it's wrong:** The price is still in the RSC payload, HTML, or network response. Client-side gating is not a security control and violates the business requirement.
**Do this instead:** Keep price in a separate collection with restricted read access. Public pages fetch only public fields. Authenticated pricing routes fetch price server-side after `requireUser("pricing:read")`.

### Anti-Pattern 4: Enabling Cache Components With Payload Admin

**What people do:** Turn on `cacheComponents` for the public site without isolating the Payload admin route group.
**Why it's wrong:** Payload's admin is not fully compatible; known issues include incorrect status codes, Activity DOM problems, and test tooling failures. A global flag affects the whole app.
**Do this instead:** Disable `cacheComponents`/`partialPrefetching` for v1. Use static generation + ISR + tagged caches. Revisit only with a verified Payload compatibility plan and route-group isolation.

### Anti-Pattern 5: Sending Email Inside `afterChange`

**What people do:** Call the email provider directly in a Payload hook and await it.
**Why it's wrong:** Hooks run inside the transaction. The transaction can still roll back after the email is sent, producing a confirmation for a lead that does not exist. Unawaited hooks are worse: they can report success after rollback.
**Do this instead:** Enqueue a durable job in the same transaction. Send email in the worker after commit, with an idempotency key.

### Anti-Pattern 6: Using Payload `autoRun` on Vercel

**What people do:** Enable `jobs.autoRun` and expect background processing in production.
**Why it's wrong:** It assumes a long-lived Node process. Vercel functions suspend; jobs may never run or may run unpredictably.
**Do this instead:** Trigger `payload.jobs.run()` from a cron-protected route or scheduled command. Keep jobs durable in Postgres.

### Anti-Pattern 7: Using Cron as the Business Scheduler

**What people do:** Schedule a reminder or SLA breach at an exact time with a Vercel Cron expression.
**Why it's wrong:** Hobby cron is once per day with ±59-minute precision; Pro is once per minute. Cron has no retries and can be delayed. Exact-time business logic will drift or fail.
**Do this instead:** Store due timestamps and compute due/overdue state on read. Use cron only to scan and enqueue notifications, with idempotency keys.

### Anti-Pattern 8: Public Blob for KYC or Confidential Documents

**What people do:** Upload IDs, reservation documents, or contracts to the public Blob store because the Payload adapter is convenient.
**Why it's wrong:** Public Blob URLs are accessible to anyone with the link. The Payload Vercel Blob adapter does not support private access. This is a reportable data breach risk.
**Do this instead:** Prefer not to custody KYC documents; store provider references only. If documents must be stored, use Vercel Private Blob via a custom server route, short-lived signed URLs, permission checks, and view auditing.

### Anti-Pattern 9: One Giant Lead Document

**What people do:** Store every note, email, consent, tour, and reservation inside a JSONB array on the lead.
**Why it's wrong:** It is hard to query, impossible to paginate, risky to update concurrently, and makes retention/consent enforcement unreliable. Audit history becomes mutable.
**Do this instead:** Use relational `lead-activities`, `consent-events`, `tours`, and `reservations` rows. Keep only a small summary on the lead.

### Anti-Pattern 10: Application-Level Inventory Checks

**What people do:** Read unit status, check it in JavaScript, then write the hold or reservation.
**Why it's wrong:** Two sales users can pass the same check concurrently and double-book a unit. Serverless concurrency makes this likely under load.
**Do this instead:** Enforce holds with a Postgres exclusion constraint and reservations with a partial unique index. Use a transaction and row locks; surface a typed conflict error to the UI.

### Anti-Pattern 11: Locale Redirect Chains

**What people do:** Redirect legacy URLs to a locale-prefixed URL, then redirect again to the canonical slug.
**Why it's wrong:** Extra hops dilute crawl equity, slow users, and create analytics noise. The legacy site already has URL equity at risk.
**Do this instead:** Map each legacy URL directly to its final canonical URL. Use config-level redirects for the fixed 12 + 58 set. Rewrite English internally rather than redirecting.

### Anti-Pattern 12: Cross-Route-Group Imports

**What people do:** Import an ops component into the public site, or import `@payloadcms/ui` into `/ops`, because it is convenient.
**Why it's wrong:** It leaks server-only code, admin styles, or PII-aware components into the wrong bundle. It also breaks the root-layout isolation that makes the architecture safe.
**Do this instead:** Share only primitives in `components/ui` and pure utilities in `lib`. Enforce import boundaries with lint rules. Keep ops and Payload admin code inside their route groups.

### Anti-Pattern 13: Running Migrations at Cold Start

**What people do:** Use `prodMigrations` or run migrations during the first request to avoid a CI step.
**Why it's wrong:** Multiple cold starts can race migrations, and a failed migration can take down the app. Builds become non-deterministic.
**Do this instead:** Run `payload migrate` before `next build` in CI against the unpooled database URL. Use `push: false` in production. Keep migrations idempotent and reviewed.

### Anti-Pattern 14: Audit as an Afterthought

**What people do:** Log to the console or write audit rows after the business operation, outside the transaction.
**Why it's wrong:** The audit trail can miss successful writes or record writes that rolled back. Compliance cannot reconstruct what happened.
**Do this instead:** Write audit and consent events in the same transaction as the business change. Fail the operation if the audit write fails. Protect the tables with database privileges.

## Build Order

The roadmap may merge phases, but the dependency order below should hold. The main rule: **identity, authorization, and audit must exist before any real PII; inventory invariants must exist before reservation UI; KYC must exist before reservation approval.**

| Phase | Architecture slice | Why now | Exit criteria |
|-------|--------------------|---------|---------------|
| **0. Foundation** | TS 6 upgrade, Payload install, Neon, Blob, migrations, env validation, root layouts, design tokens, CI | Every later phase depends on a working schema/migration/deploy loop | `payload migrate` + `next build` pass in CI; `/admin` loads; health check works; staging deploy is repeatable |
| **1. Content and public site** | `pages`, `unit-types`, `news-posts`, `media`, SEO, redirects, ISR, locale rewrite, public design system | Public site is the brand and lead engine; content model stabilizes early | 12 unit-type pages and 58 news URLs resolve; legacy redirects resolve in one hop as permanent (301/308); LCP target validated on 4G; sitemap/robots correct |
| **2. Identity, RBAC, audit, ops shell** | `users`, `access/*`, `requireUser`, `/ops` shell, login/logout, audit events, no-store rendering | PII cannot be handled safely without auth and audit | Every ops route denies anonymous/unauthorized access; role matrix tested; audit rows appear for login and a sample mutation |
| **3. Lead capture, consent, attribution** | `leads`, `clients`, `lead-activities`, `consent-events/state`, Turnstile, rate limit, dedupe, sales notification | Core value: inspiration → qualified, attributable demand | Public form creates a lead + consent + audit + job; sales receives notification; duplicate submission is idempotent; source/UTM visible in ops |
| **4. Lead inbox, pipeline, tours** | Pipeline stages, assignment, SLA timers, tasks, `tours`, confirmation job, internal calendar | Sales must act on leads before reservations make sense | Lead can be assigned, staged, and toured; confirmation email sends; SLA state is visible and computed correctly |
| **5. Inventory, pricing, holds, reservations** | `units`, `unit-prices`, `price-events`, `holds`, `reservations`, concurrency constraints, private docs | This is the operational core and the highest data-integrity risk | Two concurrent hold attempts cannot double-book; price is invisible publicly; reservation state machine is enforced; documents are private |
| **6. Client 360, KYC, enrichment, DSAR** | `kyc-checks`, consent-gated enrichment, client merge, DSAR, retention policies, DPIA | KYC is required at reservation, but only after auth/audit/inventory exist | KYC approval gates reservation approval; enrichment is consent-checked; DSAR workflow is auditable; DPIA signed off |
| **7. KPIs and reporting** | Reporting queries, materialized views if needed, source ROI, conversion, response time, unit velocity | Analytics depends on clean operational data | KPI definitions are documented; dashboards match source queries; no PII leaks into exports |
| **8. Hardening** | CSP split verification, security headers, accessibility audit, performance budget, backups/PITR test, incident runbook | Launch readiness is cross-cutting | WCAG 2.2 AA checks pass; CSP works on public and ops; restore drill succeeds; Sentry scrubbing verified |
| **9. Residents portal (later milestone)** | Separate resident auth/cookie, resident units, service requests, announcements, bookings | Different audience and compliance boundary; not needed for sales launch | Resident session cannot access staff surfaces; resident data isolated; service-request flow tested |

### Phase Ordering Rationale

- **Auth and audit before PII.** Building lead capture first creates a store of personal data with no access control or audit trail. That is the wrong order for a compliance-sensitive product.
- **Content before ops.** The public site validates the content model and gives sales something to talk about. It also forces the URL/SEO migration early, which is hard to retrofit.
- **Leads before tours.** A tour without a lead record loses attribution and follow-up. Model demand first.
- **Tours before reservations.** Reservation is a commitment; the team needs a working tour/qualification flow before inventory is locked.
- **Inventory invariants before reservation UI.** The database constraints and service transaction must be designed before building screens that assume they exist.
- **KYC at reservation, not at first contact.** Do not collect identity documents from every inquiry. Trigger KYC when commercial intent is real, minimizing PII and conversion friction.
- **Reporting last.** KPIs are a projection of operational data. Building dashboards before the underlying state machines settle produces rework.
- **Residents later.** The sales platform must prove the core auth/ops model before adding a second audience with a separate session boundary.

## Open Questions and Research Flags

1. **Payload 3.91 + Cache Components:** Re-check compatibility before enabling. The current recommendation is to keep it disabled for v1.
2. **Private Blob adapter:** Track `payloadcms/payload#16319`. Until supported, private documents need a custom route. Re-verify the CVE-2026-93363 fix in the installed adapter version.
3. **KYC vendor:** Sumsub vs Onfido vs a Philippine provider. Decision drives data residency, pricing, webhook shape, and DPIA.
4. **AMLA scope:** Confirm whether the project's reservation fees and unit sales trigger covered-transaction reporting, and the exact retention period with counsel.
5. **Consent copy:** Final English/Filipino wording, lawful basis per purpose, and whether analytics/enrichment require opt-in or opt-out.
6. **Email provider:** Resend vs Postmark vs a local provider. Confirm deliverability, DKIM/SPF, and data processing terms.
7. **Video:** Decide whether launch needs Mux or optimized MP4. This affects cost and the media pipeline.
8. **Legacy URL inventory:** Confirm all 12 unit URLs and 58 news URLs, including trailing-slash and query-string variants.
9. **Resident auth:** Confirm cookie name, session duration, and whether residents should ever share an identity with a buyer/client record.
10. **Payload admin performance:** Test the leads/pipeline admin at expected volume; if the admin UI is too slow, keep heavy operational views in `/ops` and use Payload only for content.
11. **Jobs transaction semantics:** Verify the installed Payload version's `jobs.queue({ req })` behavior and whether the job row truly joins the caller's transaction. If not, use an explicit outbox table in the same transaction and a worker that drains it.
12. **Data retention schedule:** Define retention for leads (no conversion), tours, KYC, documents, analytics, and audit. Legal/operations input required.

- [ ] Public, ops, and Payload admin have separate root layouts and no cross-group imports.
